# G-010 / WU-05 — Generic Upstream Change & Compatibility Opportunity Radar

## Purpose and evidence ceiling

WU-05 adds repository tooling only. It watches a bounded set of public first-party upstream sources, resolves PersianGravity's existing project baseline for each tracked parent product, detects a strictly newer stable release, and records version-specific research observations.

`DETECTED / DOCUMENTED != OWNER_SUPPLIED != TESTED != QUALIFIED != ADMITTED`

An observation is a research map for later package-specific qualification. It is never runtime activation authority, never mutates a package/version authority, and never acquires a commercial package.

## Shared architecture

`tools/compatibility/upstream-radar.php` is the one shared engine. Product-specific data lives in `tools/compatibility/upstream-radar-profiles.json`: existing baseline authority resolver, first-party release/docs source, bounded PersianGravity capability categories, deterministic parser, release-source mode, and observation namespace.

The engine owns profile validation, baseline loading, strict numeric version comparison, first-party retrieval, bounded documented-identifier extraction, observation validation, result aggregation, and product/version persistence. Profiles contain no operational baseline version literals.

The initial profile set is exactly Gravity Forms, Gravity Flow, GravityView, and Gravity Perks. Child packages such as GP File Upload Pro and GP Advanced Select are not scanned automatically, but the same profile contract can support them later if explicitly authorized. Arbitrary site plugins are never discovered or enrolled.

## Version and source failure semantics

Supported versions are numeric `major.minor.patch` or `major.minor.patch.revision`.

- equal → `NO_NEW_VERSION`;
- strictly newer upstream version → `NEW_VERSION_DETECTED`;
- older result, malformed/ambiguous version, malformed baseline, retrieval failure, parser drift, invalid lifecycle evidence, or source-boundary violation → visible failure.

A product/source failure is never converted to `NO_NEW_VERSION`.

Release parsing remains source-specific. Gravity Flow accepts bounded inline markup inside a release heading while still requiring the version in heading text. Gravity Perks tolerates bounded closing markup between the product name and `(vX.Y.Z)` while still requiring that exact named marker.

HTTP redirects are followed manually. Every hop must remain HTTPS and inside the explicit first-party host allowlist before the next request is made; an unapproved redirect target, missing `Location`, non-2xx terminal response, or redirect loop fails visibly.

The live workflow also records source-heading diagnostics. Rolling sources are checked against the highest `MODEL_REVIEWED` observation from the same first-party release URL. A lower live result fails as stale/ambiguous instead of silently becoming an all-clear. Historical or unresolved observations do not become runtime or upstream authority merely by existing in the repository.

## Documentation-only classifications

The governed vocabulary is:

- `NO_RELEVANT_DOCUMENTED_CHANGE`
- `DOCUMENTED_CONTRACT_CHANGE`
- `POTENTIAL_BETTER_SEAM_FOUND`
- `REQUALIFICATION_RECOMMENDED`
- `PACKAGE_REQUIRED_FOR_PROOF`
- `MODEL_REVIEW_REQUIRED`

`POTENTIAL_BETTER_SEAM_FOUND` is invalid without explicit supporting official evidence. Deterministic automation does not infer compatibility or semantics from keywords. A newly detected version generated by automation therefore starts as `MODEL_REVIEW_REQUIRED` plus `PACKAGE_REQUIRED_FOR_PROOF`.

During WU-05 implementation, current detections were semantically reviewed against official docs and committed as `MODEL_REVIEWED` documentation-only observations.

## Observation area and persistence

Records live at:

`tools/compatibility/upstream-observations/<product>/<version>.json`

Each record carries the resolved project baseline + authority path, `DETECTED_ONLY`, package state, timestamp, official provenance, classifications, capability observations, semantic-review state, and mandatory `PACKAGE_REQUIRED_FOR_PROOF` boundary. Terminal products additionally retain explicit lifecycle evidence. The validator rejects docs-only `QUALIFIED` or `ADMITTED` claims.

`.github/workflows/upstream-compatibility-radar.yml` runs weekly and exposes `workflow_dispatch`. It also has a path-bounded pull-request trigger so the live public-source boundary can be exercised on the exact PR head before merge.

Scheduled/manual persistence uses one deterministic branch, `automation/upstream-radar-observations`. It can modify only the four approved observation namespaces, never pushes directly to `main`, and never auto-merges. Evidence files for persistence are written under `$RUNNER_TEMP`, outside the Git worktree.

Repeat product/version candidates are deduplicated. Automation-generated unresolved observations may be refreshed when official evidence materially changes. A `MODEL_REVIEWED` observation is never overwritten by automation. If stored source fingerprints for a reviewed observation differ from current first-party evidence, persistence returns `REVIEWED_SOURCE_CHANGED_REVIEW_REQUIRED`; the CLI converts that into a non-zero run and includes the failure in the job summary rather than silently losing the review signal.

## Source fingerprint root-cause disposition — 2026-10-24

**Scope: Gravity Flow and Gravity Perks first-party sources only; documentation/evidence review, not a product or radar-code repair.**

### Why scheduled persistence stopped

`PGR_Upstream_Radar::persistCandidate()` compares the SHA-256 of each *entire fetched page* to the source fingerprints in an existing `MODEL_REVIEWED` observation. A mismatch yields `REVIEWED_SOURCE_CHANGED_REVIEW_REQUIRED` and `assertPersistenceOutcome()` fails visibly. This is a deliberate provenance safety gate. It does **not** establish whether the reviewed version's own release text changed. New rolling-release headings, navigation or page decoration, and edits to reviewed notes can all change the hash. Merely allowing a newer reported version must never bypass review of material historical changes.

The former scheduled failures were reported at the persistence boundary, not as authenticated WordPress/browser or package failures. The historical failed workflow runs are **identifiable** in GitHub Actions; however, the complete historical upstream HTML snapshots and byte-for-byte content diffs were **not recovered** during this review. Absence of the snapshots must not be conflated with an inability to identify the failed runs. In particular, a historical SHA-256 and a human summary cannot reconstruct the HTML used to calculate the digest. Therefore the cause of *each past page change* (new release vs formatting vs material edit) remains **NOT_PROVEN**.

**New directly executed evidence:** the PR-triggered four-product scan [40085682249](https://github.com/rezahh107/PersianGravity/actions/runs/40085682249) and manual read-only `workflow_dispatch` [40086954962](https://github.com/rezahh107/PersianGravity/actions/runs/40086954962) independently produced identical *current* full-page hashes:
- Gravity Flow changelog: `fac0e6b6ca19525c5896a5a45eb3cb6965482085764c199086467518bc37bdd4`.
- Gravity Wiz Weekly #269: `e0b47f93f3f536dc2849d5810e17114d670cb42b9c2015bfc8507358a2b8769a`.
- Spellbook documentation: `b48861b873af46bcb29c4e4151d4931a1786811c38b5ba10bd78fa60fe097914`.

These artifacts retain per-source hashes, version candidates and bounded heading diagnostics, **not raw source snapshots**. The manual scan proves live discovery, not persistence: its persistence job was skipped. The current hashes differ from reviewed historical records, but equality between the two October 24 runs does not prove equality with September's content.

### Design assessment, preservation and next review gate

The whole-page hash is overly broad as a *diagnostic discriminator*, but it remains a safe **fail-closed legacy provenance gate** in the absence of reliable prior version-specific source snapshots. Replacing it immediately with a new hash of today's selected text would create an unsupported claim about the *past*. Ignoring it merely because a page grew would also conceal possible edits to already reviewed release notes. Consequently this checkpoint **does not relax or change persistence, parsing, source-fingerprint or consistency code** and does not mark the historical mismatches resolved.

A future scoped digest is justified only if actual first-party HTML variants and a **trusted reviewed version-specific baseline** can establish complete release-content boundaries and relevant Spellbook install/license/migration sections. Its regression evidence must distinguish: unrelated page decoration, new release headings, genuine edits within reviewed notes, absent/duplicate/malformed headings, modified lifecycle instructions, missing previous snapshots, and source-version ambiguity. Unknowns must continue to fail with `MODEL_REVIEW_REQUIRED`; all newer versions retain `PACKAGE_REQUIRED_FOR_PROOF`. This is a qualification requirement, **not authorization to auto-bootstrap a review baseline from today's content**.

**Disposition:** existing historical source-review blockers remain **OPEN / NOT_PROVEN** pending trustworthy historical source material or an explicit new source-content review with dated, version-scoped provenance. The four-product *read-only* monitoring path is **VERIFIED**; historical persistence safety cannot be cleared from the available evidence. Do not start WU-06 until these outstanding reviews and any eventual focused code qualification are completed. No G-011 work, release, package swap or production change is implied.
